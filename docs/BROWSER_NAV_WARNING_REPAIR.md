# Browser NAV warning consistency — 27 October 2026

## Two reproduced browser defects

The server merge-counter repair in PR #50 did not change browser-cache validation. The browser had two different warning-handling problems:

1. `validateCachedFund` rechecked the stored NAV observations but appended its result to any saved generated jump counters. A backup or existing cache could retain an obsolete counter, or show several conflicting counts for the same history.
2. `mergeCachedFund` removed every message beginning `Unresolved discontinuity:` before recalculating price jumps. That was broader than the server's exact-counter rule and could erase an unrecognized source-discrepancy warning from the selected input history.

These are warning-accounting defects. They do not identify a correct replacement NAV for an unexplained source-price anomaly.

## Bounded repair

Only the exact autogenerated message is replaceable:

`Unresolved discontinuity: <integer> single-observation move(s) exceed 40%; derived analytics are blocked.`

The browser now removes that exact counter before using its existing NAV validation result. Actual large movements regenerate a blocking warning with the current count. An obsolete generated counter can no longer override the observed history during cache validation or backup restore. Refresh merging uses the same exact-message test rather than the broad prefix.

Unrecognized warning messages in the selected history, invalid-NAV evidence and conflicting-observation evidence are not stripped by this counter replacement. Existing history-selection and retained-quality rules are otherwise unchanged.

The production change does not alter any NAV, date, scheme identity, retrieval timestamp, return formula, 40% threshold, cache resource limit, source request, collector schedule, corporate-action rule, archive checkpoint or published ranking-index eligibility. Original archive provenance and its warning record remain intact; recomputed browser warnings describe the actual validated browser observation set.

## Regression evidence

The seven new tests were committed before implementation. [Dashboard checks #40455167948](https://github.com/Vasuki8/mutual-fund-dashboard/actions/runs/40455167948) reproduced all seven failures while the original 566 tests passed. The cases exercise cache validation, mismatched counts, preserved invalid/conflicting/unknown warnings, normal and late refresh merging, archive provenance, and a complete backup-restore/refresh/export sequence. They call the real production functions, with synthetic NAVs and no provider/network mocks.

A separate corrected-code run and final pull-request checks must pass before merge. The failing regression run is expected evidence of the original defects, not a deployment failure.

## Operational meaning

After deployment, loading stored histories through the updated cache validator re-evaluates their generated jump counters. The existing cache read, refresh and backup paths do this without clearing a user's saved funds or notes. Do not ask users to delete their browser database to apply this repair.

A warning may correctly remain because an actual price jump, invalid observation or conflicting observation remains. The previously investigated Quant source spikes (100176/100177), PPFAS reference differences, and historical zero-NAV gaps are not repaired by this change. A passing code test is not evidence that any archive quality count has fallen. The archive and browser cache remain separate stores.
